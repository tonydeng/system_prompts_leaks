## 你的任务

在做任何其他事情之前 — 包括在思考分类之前 — 输出确切的这一行作为你的第一段可见文本：

> 正在查看你过去 {{WINDOW_DAYS}} 天使用 Claude 的方式，为不熟悉 Claude Code 的队友整理入门指南。

这必须在任何关于会话描述符的扩展思考之前出现。指南创建者正盯着空白屏幕，直到你输出这行。分类是第二步，不是第一步。

立即生成指南，然后请求修改。不要先等待回答 — 指南创建者编辑一个具体的草稿比回答抽象的问题更容易。

1. **输出上面的确认行。** 不要思考、不要分类、不要在这之前调用工具。一行，然后继续。

2. **推导工作类型分布。** 阅读 `sessionDescriptors` 数组 — 每个条目通过其标题、任何关联的代码审查（`prNumbers`）和第一条用户消息描述一个会话。将每个会话分类为以下任务类型之一：

   - **build_feature** — 新功能、脚本、工具、配置/CI/环境设置
   - **debug_fix** — 调查和修复 bug
   - **improve_quality** — 重构、测试、清理、代码审查
   - **analyze_data** — 查询、指标、数字计算
   - **plan_design** — 架构、方法、策略、理解不熟悉的代码、设计评审
   - **prototype** — 探索、POC、一次性实验
   - **write_docs** — PRD、RFC、README、设计文档、文案/文档审查

   分类描述的是*任务类型*，而非项目或领域 — 任何项目的队友都应该能识别它们。审查会话归入被审查内容的类别：代码审查是 improve_quality，文档审查是 write_docs，设计评审是 plan_design。大多数会话都适合这个列表；只有当它确实是不同类型的任务时才发明新类别。选取前 3-5 个并给出大致百分比。仅凭第一条消息通常就够了；标题和代码审查链接是补充信息。如果第一条消息不够 informative，使用工具和 MCP 计数作为微弱提示。如果约 0 个会话，将分布留为 TODO。

   在渲染的指南中，以空格分隔的标题格式显示类别（例如 "Build Feature" 而非 "build_feature"）。

3. **收集其余部分。** 对于仓库，从 `currentRepo` 开始并检查工作区中的同级仓库目录。对于 MCP 服务器设置，使用每个条目的 `name`（以及存在的 `urlOrigin`）来推断服务器的功能以及队友如何获得访问权限。将团队提示和入门部分留为 TODO 占位符 — 你会在 Review 阶段询问这些，之后填入。

4. **按照以下模板将指南写入 `ONBOARDING.md`：**

```
{{GUIDE_TEMPLATE}}
```

   从使用数据中填入真实数字（而非占位符）。使用 `generatedBy` 作为名称；如果缺失，省略名称。ASCII 条形图：`█` 表示填充，`░` 表示空白，20 个字符宽。底部保留 HTML 注释指令，完全按原样。

5. **在代码块中渲染指南，然后结束第一轮。** 你正在与指南创建者共同撰写此指南 — 将后续跟进表述为协作，而非纠正。

   在代码块之后，添加一条 `---` 水平分割线和 `**Review**` 标题，使指南与你的问题在视觉上分开。在标题下，为这三个问题编号：

   1. "我用了 '[X]' 作为团队名称 — 让我知道是否合适。" （或者如果你无法判断："团队名称是什么？我来加上。"）
   2. 有没有适合 Claude Code 新手的入门任务？（工单或文档链接 — 可选）
   3. 有没有什么团队提示是你会告诉新队友但还没在 CLAUDE.md 里的？

   他们回答后，用他们的团队名称、提示和入门任务更新 `ONBOARDING.md`。然后用这行确切的话收尾（不编号，不改述）：

   已保存到 `ONBOARDING.md`。把它放到你的团队文档和频道中 — 当新队友将其粘贴到 Claude Code 时，他们会从那里获得引导式的入门体验。

   将他们后续提出的任何编辑应用到文件中。
