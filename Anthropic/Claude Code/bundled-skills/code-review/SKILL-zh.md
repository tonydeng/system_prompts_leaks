description: 审查当前 diff 中的正确性 bug 以及复用/简化/效率清理，按指定努力等级进行（low/medium：更少、更高置信度的发现；high→max：更广的覆盖范围，可能包含不确定的发现；ultra：云端深度多智能体审查）。传 --comment 将发现作为行内 PR 评论发布，或传 --fix 在审查后将发现应用到工作树。
---

`high effort → 3+5 角度 × 6 候选 → 1 票验证（召回偏向）→ ≤10 条发现`

你在高努力等级下为**召回**而审查：捕捉一个细心的审查者在一次审阅中会捕捉到的
每一个真实 bug。在这个级别，捕捉真实 bug 比避免误报更重要。倾向于
多报而非漏报。

## 阶段 0 — 收集 diff

运行 `git diff @{upstream}...HEAD`（或 `git diff main...HEAD` / `git diff HEAD~1`
如果没有上游）获取审查中的统一 diff。如果有未提交的变更，或范围 diff 为空，
也运行 `git diff HEAD` 并将工作树变更纳入范围——审查通常在提交前运行。
如果传入了 PR 号、分支名或文件路径作为参数，则审查该目标。将此 diff 视为审查范围。

## 阶段 1 — 查找候选（3 个正确性角度 + 3 个清理角度 + 1 个高度角度 + 1 个规范角度，各最多 6 个）

通过 Agent 工具运行 **8 个独立的查找角度**。每个
产出**最多 6 个候选发现**，包含 `file`、`line`、一行 `summary` 和一个具体的
`failure_scenario`。

### 角度 A — 逐行 diff 扫描

逐行阅读 diff 中的每个 hunk。然后阅读每个 hunk 所在函数的完整代码——
被触碰函数中未变更行的 bug 也在范围内（PR 重新暴露或未能修复它们）。
对每一行问：什么输入、状态、时序或平台会让这行出错？寻找
反转/错误的条件、差一错误、null/undefined 解引用、缺失的 `await`、
假值零检查、错误变量的复制粘贴、catch 中吞掉的错误、未转义的正则元字符。

### 角度 B — 移除行为审计

对于 diff 删除或替换的每一行，命名它所执行的不变量或行为，
然后在新代码中搜索该不变量在哪里被重新建立。
如果找不到，那就是一个候选：一个被移除的守卫、一个被丢弃的错误
路径、一个被收窄的验证、一个被删除的覆盖真实场景的测试。

### 角度 C — 跨文件追踪

对于 diff 修改的每个函数，找到其调用者（Grep 搜索符号）并
检查变更是否破坏了任何调用点：新的前置条件、改变的
返回结构、新的异常、时序/顺序依赖。同时检查被调用者：
同一 PR 中的并行变更是否让某个调用变得不安全？

### 复用

上面的角度寻找 bug；这个和接下来两个寻找变更代码中的清理。
标记重新实现了代码库已有功能的新代码——Grep 共享/工具模块和变更
附近的文件，并指出应调用的现有辅助函数。

### 简化

标记 diff 引入的不必要复杂性：冗余或可推导的状态、
略有变化的复制粘贴、深层嵌套、遗留的死代码。指出
完成相同工作的更简单形式。

### 效率

标记 diff 引入的浪费工作：冗余计算或重复 I/O、
独立操作串行执行、启动或热路径中添加的阻塞工作。
同时标记从闭包或捕获环境构建的长生命周期对象——它们在对象
生命周期内保持整个外围作用域存活（当该作用域持有大值时是内存泄漏）；
优先使用只复制所需字段的 class/struct。指出
更廉价的替代方案。

### 高度

检查每个变更是否在正确的深度实现，而非脆弱的
创可贴。在共享基础设施上层叠特殊情况是修复
不够深入的信号——优先泛化底层机制而非添加
特殊情况。

### 规范（CLAUDE.md）

找到管辖变更代码的 CLAUDE.md 文件：用户级
~/.claude/CLAUDE.md、仓库根目录的 CLAUDE.md，以及任何位于变更文件祖先
目录中的 CLAUDE.md 或 CLAUDE.local.md（目录的 CLAUDE.md 只适用于该目录
及其下方的文件）。阅读每个存在的文件，然后检查 diff 是否明显违反
其声明的规则。

只有当你能引用确切的规则和违反它的确切行时才标记违规——
不要风格偏好，不要模糊的"文档精神"
推断。在发现中，命名 CLAUDE.md 路径并引用规则，使
报告可以引用它。如果没有 CLAUDE.md 适用，此角度返回空。

清理、高度和规范候选使用相同的
`file`/`line`/`summary` 形状；在 `failure_scenario` 中，陈述具体
成本（什么被重复、浪费、更难维护，或哪条 CLAUDE.md 规则
被破坏）而非崩溃。当输出上限迫使裁剪时，正确性 bug 始终优先于清理、
高度和规范发现。

将每个有可命名失败场景的候选通过——静默丢弃
半信半疑候选的查找器会绕过验证步骤，是
遗漏的主要原因。

## 阶段 2 — 验证（1 票，召回偏向）

对近似重复项去重（相同缺陷、相同位置、相同原因 → 保留一个）。对于
每个剩余候选，通过 Agent 工具运行**一个验证器**：
给它 diff、相关文件和候选；它返回
**CONFIRMED / PLAUSIBLE / REFUTED** 之一。

**默认 PLAUSIBLE** —— 当状态是现实的时候，不要因为候选"投机"或
"依赖运行时状态"就反驳它：并发竞争、
在罕见但可达路径上的 nil/undefined（错误处理器、冷缓存、缺失的
可选字段）、被当作缺失处理的假值零、代码未排除的边界上的差一错误、
重试风暴/部分失败、丢失锚点的正则/白名单。这些都是 PLAUSIBLE。

**REFUTED** 仅当可从代码构造时：事实上错误（引用
实际行）；可证明不可能（类型/常量/不变量——展示它）；已在
此 diff 中处理（引用守卫）；或纯风格且无可观察效果。

保留 **CONFIRMED 和 PLAUSIBLE**。丢弃 REFUTED。

## 输出

以最多 10 个对象的 JSON 数组返回发现：

```json
[
  {
    "file": "path/to/file.ext",
    "line": 123,
    "summary": "one-sentence statement of the bug",
    "failure_scenario": "concrete inputs/state → wrong output/crash"
  }
]
```

按严重程度从高到低排列。如果超过 10 个存活，保留 10 个最
严重的。如果没有通过验证的发现，返回 `[]`。
