# 将设计系统同步到 claude.ai/design

## 用途

**Claude Design**（claude.ai/design）是 Claude 的设计工具：用户提示设计智能体，它构建可工作的 UI——屏幕、流程、原型——从真实 React 代码在浏览器中实时渲染。开箱即用时，它使用通用组件进行设计。此技能改变了这一点：它将用户的设计系统仓库转换为 Claude Design 消费的格式并上传，此后**设计智能体使用客户的真实组件进行构建**——它产出的每个设计都符合品牌规范，由真实零件组成，并与工程师可交付的代码 1:1 映射。

这一框架应驱动此技能中的每个判断决策，因为每个上传的产物都是该智能体（或驾驭它的人类）的输入：

| 上传产物 | 消费者 | 用途 |
|---|---|---|
| `_ds_bundle.js` + `_vendor/` | 设计智能体的运行时 | 它产出的每个设计都从 `window.<globalName>.*` 渲染这些真实编译组件 |
| `styles.css`, `fonts/`, `tokens/`, `_ds_bundle.css` | 每个渲染的设计 | 外观——令牌、字体和组件样式，全部可从 `styles.css` 的 `@import` 闭包到达（设计仅接收该闭包） |
| `<Name>.d.ts`（`<Name>Props`） | 设计智能体 | 它编码所依据的 API 契约 |
| `<Name>.prompt.md` | 设计智能体 | 它的使用参考——如何组合组件，含示例 |
| `<Name>.html` 预览卡片 | 组件选择器中的人类 | 他们如何发现组件并信任同步 |
| `_ds_sync.json` | 未来的同步 | 同步锚点——内容哈希让重新同步（任何机器）跳过未更改组件的重新验证，并精确计算要上传/删除的内容 |

这就是为什么保真度是整个游戏的核心：一个渲染错误的组件在这里渲染错误，**智能体用它构建的每个设计**中都会渲染错误，而错误的 `.d.ts` 或误导性的 `.prompt.md` 会让智能体在所有地方误用 API。子技能中的验证循环正是因此存在——它们不是繁文缛节。

转换器从仓库自身的 `dist/` 确定性地构建上述所有内容。有 Storybook 时，预览来自仓库的 stories，并针对其自身的 storybook 渲染进行验证（作为本地参考保留，从不上传）。没有 Storybook 时，每个组件仍然完整可用，丰富的预览从仓库自身的使用示例中为用户划定范围的组件编写，按绝对标准评分。**核心原则：交付客户已经构建的东西**——bundle 是他们编译的 `dist/`，绝不是重新实现。

你有一个 `DesignSync` 工具，可读写用户的 claude.ai/design 项目。如果工具调用因授权错误失败，请逐字将其指引转达给用户——工具的消息是环境感知的（在交互式终端中它提及 `/design-login`；在 claude.ai/code 等无头会话中它指向在那里可用的路径）——并在他们采取行动后重试。

## 0. 首次同步？在任何工作之前设定期望

完成的同步总是会在 `.design-sync/config.json` 中留下 `projectId` 和 `pkg`。如果两者都存在，这是重新同步——跳过本节（§2 涵盖了如何遵循先前状态）。（如果存在 `design-sync.config.json`——配置的旧名称和位置——请移动它：`mkdir -p .design-sync && mv -n design-sync.config.json .design-sync/config.json`，提交移动，然后应用相同的测试。）其他情况——完全没有配置，或由从未完成的运行留下的部分配置——按首次处理：在做任何其他事情之前，提前告诉用户：

- 未找到完成的同步——这是首次导入。
- 此技能尝试对其设计系统进行**高保真**导入：默认情况下，这意味着迭代构建并目视验证每个组件预览的质量，在大型仓库上可能需要**长达数小时**。
- 他们可以随时中断——运行中发送消息检查进度或重新定向方向是受欢迎的，不会破坏任何东西。
- 首次导入进入一个**为其创建的新 Claude Design 项目**（§1）。需要他们批准的一切都发生在**开始阶段附近**——创建该项目，以及覆盖本次运行上传内容的一次批准。之后，**已验证的组件随着运行进展出现在项目中**：他们可以随时打开项目观看它填充，末尾没有任何东西等待他们的批准。
- 运行过程中会记录配置和笔记，因此未来的同步更快且大部分是确定性的。

（如果 §1 将本次运行路由到现有项目——用户重新采用一个，或由中止运行留下的 `projectId`——部分内容不适用；根据 §1 的路由结果调整期望。）

然后确认他们是否要继续——此过程可能消耗大量 token（`AskUserQuestion`：继续完整的搞保真同步，或先调整范围）。如果他们的请求已经确认了时间/成本，记录并继续，不再重复询问。

## 1. 选择目标项目

如果 `DesignSync` 不在你的工具列表中，先通过 `ToolSearch(query: "select:DesignSync")` 加载它。目标通过以下三种方式之一选择，按优先级排序：

- **已固定**：`.design-sync/config.json` 有 `projectId` → 那就是目标。`DesignSync(get_project)` 确认它仍然存在且为 `PROJECT_TYPE_DESIGN_SYSTEM`，提及你正在同步到哪个项目，仅当它消失或用户重定向时重新询问。
- **全新——首次默认**：没有固定 → **创建新项目**。全新项目是本次运行唯一拥有全部内容的目标；这种所有权使得增量上传（§3）可以一次性批准，这也是为什么这里从不提供现有项目——将首次导入倒入已有文件的项目会向使用它的人展示半导入的混合状态，没有同步锚点来区分其文件与本次运行的文件。使用 `DesignSync(list_projects)` 选择非冲突名称（重复会被拒绝并浪费一次往返），通过 `AskUserQuestion` 确认名称，然后才调用 `DesignSync(create_project)`——它会引发自己的权限提示，未确认的创建可能使无人值守的会话停滞。如果该提示被拒绝，停下来问用户该怎么做 differently；绝不未经要求重试，绝不在没有目标的情况下继续。一种挽救情况：一个明显由本仓库先前中止运行留下的项目（它有此技能会提议的名称——`list_files` 确认它确实为空，因为 `list_projects` 不显示文件计数）可以提供复用而不是创建另一个，或注明可安全删除。
- **重新采用——仅在用户明确要求时**：用户指定一个现有项目（按名称或 UUID；通常是重新采用先前同步上传到的项目，在配置丢失后）。`DesignSync(get_project)`，检查 `type` 是否为 `PROJECT_TYPE_DESIGN_SYSTEM`，然后用通俗语言（无工具术语）警告他们同步可能覆盖或删除其中已有文件——例如"提醒你：同步到那个现有项目意味着我可能替换或删除它已包含的文件，使其最终匹配此仓库。如果其中有任何非本仓库的内容，可能会丢失——要我继续，还是改为创建一个新项目？"——仅在他们的确认后继续。这种明确要求是未固定的运行进入已有项目的唯一途径。

**在确定时记录固定。** 目标确定的时刻——创建、复用或重新采用——**立即将其 `projectId` 记录到 `.design-sync/config.json`**，在任何上传之前。这是此技能的唯一记录规则：之后任何时刻的死亡留下的是一个已固定的配置，因此重试通过原子路径修复同一个项目，而不是创建副本并孤立原始项目。（子技能原子部分中的上传后记录步骤只是此规则的后备。）

**路由上传路径。** 在本次运行开始**之前**固定的 `projectId` 始终走**原子路径**（子技能的上传部分）——即使其项目最终为空；批量重新上传在那里没问题，一条规则胜过特殊情况。否则由远程决定，通过对目标的免提示 `DesignSync(list_files)`：

- **空**（正常情况——本次运行刚创建它）→ **增量路径**（§3）：一次预先批准，然后已验证组件随运行进展上传。
- **非空**（重新采用的项目）→ **原子路径**：它可能正在使用中，因此在运行结束时一次性更新所有内容，在一切验证之后。

路由器仅决定**上传**路径。**验证**范围是锚点的工作：有 `_ds_sync.json` 的项目让重新同步驱动器跳过未更改组件；没有锚点意味着一切都要验证，无论走哪条上传路径。

## 2. 探索，然后写配置

工作流程是**探索仓库 → 写 `.design-sync/config.json`（§1 的固定已创建目录和文件——读取它并添加内容，绝不丢弃 `projectId`；`mkdir -p .design-sync` 作为遗留状态的安全网保留）→ 从中确定性地运行转换器**。转换器的发现是基于启发式的；每个启发式都有配置覆盖（在子技能暂存脚本后：`grep -r ASSUMPTION .ds-sync/*.mjs .ds-sync/lib/*.mjs` 列出它们），因此不匹配默认值的仓库写配置，而非改代码。仅作为最后手段编辑 `lib/*.mjs`（见子技能的逃生舱章节：storybook §5，package §Troubleshooting）。

**上传格式就是契约；转换器是通往它的确定性路径，不是唯一路径。** 应用消费的内容完全由输出布局指定：`_ds_bundle.js` + `@ds-bundle` 头部、`styles.css`、`components/<group>/<Name>/{.html,.jsx,.d.ts,.prompt.md}` 带有 `@dsCard` 首行、`_preview/`、`_vendor/`、`fonts/`、`_ds_sync.json`（见子技能的布局和上传章节）。

脱离脚本的布局也应尽可能产出 `_ds_sync.json`。对于 package 形态，`lib/sync-hashes.mjs` 提供 `styleShaFor`/`renderHashFor`/`sourceKeyFor`；信封为 `{shape, styleSha, renderHashes, sourceKeys, keyRecipe, scriptsSha, sourceHashes, auxSha, bundleSha12}`（见 `package-build.mjs` 中的 sidecar 块——`sourceHashes` 本身来自 `lib/bundle.mjs` 的 `stampHeader`；`sourceKeys` 可省略，仅意味着更改的产物需重新验证）。storybook 形态的配方需要脱离脚本生成器可能没有的 story 事实；省略 sidecar 是诚实的选择——下一次同步只是没有锚点并重新验证一切，这是正确的。

手工产出布局时容易遗漏的一个不变量：渲染的设计仅接收 `styles.css` 的传递性 `@import` 闭包。任何真实组件 CSS（`_ds_bundle.css`）必须从 `styles.css` 中 `@import`——直接链接它的卡片对设计证明不了什么。

对于确实在转换器信封之外的仓库（非 esbuild 可打包的构建、异域工具链），用仓库允许的任何方式产出布局。门禁不会移动：`package-validate.mjs` 必须干净退出，每个 story 在上传前必须评分——storybook 形态中来自真实截图对，package 形态中按绝对标准。脱离脚本生成是正当的；脱离脚本的*验证*不是。

**来自先前运行的状态。** 如果 `.design-sync/config.json` 或 `.design-sync/NOTES.md` 已存在，先读取两者并遵循其中的内容——它们保存着早期同步的修正。**每当用户在运行中告诉你一个问题**（一个路径、一个构建标志、一个要跳过的组件、一个包管理器怪癖），立即持久化它，这样下一次同步不需要再被告知：映射到 `cfg.*` 字段的值放入 `.design-sync/config.json`；其他内容作为要点放入 `.design-sync/NOTES.md`。两者在最后提交（子技能说明何时）。

1. **用仓库自身的包管理器忠实安装。** 使用仓库固定的 node 版本（`.nvmrc` / `engines.node`），然后通过 lockfile 检测：`yarn.lock` → `yarn install --immutable`；`pnpm-lock.yaml` → `pnpm i --frozen-lockfile`；`bun.lockb`/`bun.lock` → `bun install --frozen-lockfile`；`package-lock.json` → `npm ci`。
2. **确定源形态。** 如果 `.design-sync/config.json` 已存在且有 `"shape"` 字段，使用它。否则 `Glob` 搜索 `**/.storybook/main.*` 和 `**/storybook/main.*`（有些仓库省略点号；排除 `node_modules`）——monorepo 设计系统将其放在子包中，所以绝不假设它在仓库根目录：
   - 任何匹配 → `shape = 'storybook'`。匹配项的祖父目录是要运行的包。找到多个 → `AskUserQuestion` 哪个是设计系统的；该目录成为 `storybookConfigDir`。**不要因为 `.storybook` 不在仓库根目录就回退到 package。**
   - 找到 `*.stories.*` 文件但目标中没有 `.storybook/` 目录 → `AskUserQuestion`："找到了 story 文件但这里没有 `.storybook/`——此仓库中其他地方有 Storybook 配置吗（例如 monorepo 中的 `apps/storybook/.storybook`）？"如果他们指向一个 → `shape = 'storybook'`，将该路径记录为 `storybookConfigDir`。如果他们说没有 → `shape = 'package'`。
   - 没有 `.storybook/` 且没有 `*.stories.*` → `AskUserQuestion` 是否存在 Storybook。如果他们指向一个，记录为 `storybookConfigDir` 并设 `shape = 'storybook'`。如果没有，`shape = 'package'`。

然后 `Read` `<skill-base-dir>/storybook/SKILL.md` 或 `<skill-base-dir>/non-storybook/SKILL.md` 并从那里开始遵循（storybook 的会在重叠处指回 package 的共享表格）。写配置时将 `"shape"`（以及 `"storybookConfigDir"` 设置时）记录到 `.design-sync/config.json`，以便重新同步跳过检测。两种形态都运行 `<skill-base-dir>/package-build.mjs` 作为转换器入口，运行 `<skill-base-dir>/resync.mjs` 作为唯一的重新同步驱动器（构建 → diff → 验证 → 范围化捕获，一个判定 JSON）；共享适配器位于 `<skill-base-dir>/lib/`，`<skill-base-dir>/storybook/` 持有 storybook 专用工具（`compare.mjs`——预览与 storybook 匹配；`probe.mjs`——provider 推断回退）。

## 3. 增量上传序列（首次同步到空项目）

在增量路径上（§1），用户在早期批准一次上传，然后在运行仍在进行时观看已验证组件出现在他们的项目中——而不是在最后等待数小时进行一次批量上传。本节是共享机制；子技能说明每步**何时**触发（其自身的构建和验证门禁，在此标记为"incremental path"）。子技能上传章节的机制也适用于此处的每次写入：每次 `write_files` 调用 ≤256 文件，二进制密集目录用更小的块，上传卫生，以及保留在本地的列表。

### 打开上传通道——在子技能的首次干净构建门禁

1. **先用通俗语言解释批准。** 在询问之前，告诉用户他们即将批准什么，无工具术语（不提 "plan"、"glob" 或工具方法名）：例如*"我现在请求一次批准，涵盖将本次运行产出的所有内容上传到新项目——以及清理后续重建丢弃的任何文件。你不会再被提示；组件在验证后会出现在项目中。"* 批准对话框自身显示结构化路径列表；这条消息是让从未同步过的人理解该对话框的关键。
2. `DesignSync(finalize_plan)`，参数为 `localDir: "./ds-bundle"`，`writes: ["components/**", "tokens/**", "fonts/**", "_vendor/**", "_preview/**", "guidelines/**", "_ds_bundle.js", "_ds_bundle.css", "styles.css", "README.md", "_ds_sync.json", "_ds_needs_recompile"]`，`deletes: ["components/**", "tokens/**", "fonts/**", "_vendor/**", "_preview/**", "guidelines/**"]`。删除 glob 是使下方运行结束对账免提示的原因——而且它们在这里同意微不足道：项目开始为空，所以任何可删除的都是本次运行上传的。返回的 `planId` 服务于整个运行（它在会话期间存活）。运行中因上下文重置丢失 → 再次 `finalize_plan`，一次新的批准，在上传更多内容之前。整个会话死亡根本不恢复此路径：重试到达时已固定（§1）并正确走原子路径——这是预期的，不是需要绕过的 bug。
3. **如果批准被拒绝，停下来询问——绝不静默继续，绝不未经要求再次提示。** 用通俗语言说明什么被拒绝及其涵盖内容（"将本次运行输出上传到新项目的一次性批准"），然后提供：再次尝试批准；定位到不同项目；或在本地完成构建和验证不上传。仅本地 → 运行正常进行，只是不上传任何内容，运行结束报告同时交付 `ds-bundle/` 路径和项目 URL（`https://claude.ai/design/p/<projectId>`——固定已记录，因此后续同步找到此项目而非孤立它）。不同项目 → 通过 §1 的重新采用询问和路由器，如同任何其他明确选择，包括固定：非空 → 原子路径，此计划放弃；空 → 用新的批准恢复此处。
### 推送每个已验证批次

在第一批组件通过子技能的完成栏之前不上传任何内容。**首次推送将共享基础文件与该批一起携带**：`_ds_bundle.js`、`_ds_bundle.css`、`styles.css`、`README.md`、`_vendor/**`、`tokens/**`、`fonts/**`、`guidelines/**`，加上该批的 `components/<group>/<Name>/` 目录和 `_preview/<Name>.*` 文件。它们一起传输有两个原因：用户在项目中看到的第一件事是真实组件，而不是声称上传了东西的空壳——而且到首批时间，共享文件已证明自己的价值，因为评分这些组件练习了完全相同的 bundle、CSS 和字体。首次推送是项目的首批内容也是最大的一次，所以需要完整围栏：先哨兵（`write_files` `_ds_needs_recompile`——它将应用的清单/复制机制围栏以防半上传状态），然后是文件，然后重写哨兵（此路径上的每次推送都以重写哨兵结束——这就是让应用下次打开时刷新项目视图的原因）。在此推送时醒目输出项目 URL——`https://claude.ai/design/p/<projectId>`——这是项目首次有内容可看的时刻。

之后每个通过完成栏的批次：`write_files` 其 `components/<group>/<Name>/` 目录和 `_preview/<Name>.*` 文件，然后重写哨兵——新卡片在用户下次打开或刷新项目时出现。报告批次进度时，包含项目 URL，使新卡片一键可达。如果自上次推送以来运行了完整重建（全局配置修复落地），再次包含共享基础文件：修复在本地重写了 bundle/CSS/字体，不重新推送它们，每个在其后验证的组件都会渲染为过时的远程版本，直到收尾。它们在已批准的计划中且是幂等的，重新推送没有成本。

后续批次推送不需要前导围栏——它们简短且始终以重新武装结束，所以未围栏的窗口可忽略不计（上面的首次推送和下面的长收尾是需要先围栏的）。批次是渐进可见性，不是正确性机制：收尾保证最终状态，所以不要纠结批次组合——一个先推送后被返工的组件只需重新推送。

### 收尾——在子技能的最终门禁之后

1. **先哨兵，然后完整内容写入。** 先于一切重写 `_ds_needs_recompile`——应用在用户打开项目时清除哨兵（此路径邀请运行中打开），而收尾是最长的写入+删除段，所以在此重新围栏是防止半应用状态被消费的关键。然后计划 writes 中除 `_ds_sync.json` 外的一切，分块。重新上传未更改的文件是幂等且廉价的；此遍覆盖批次遗漏的任何内容和最终重建更改的任何内容，使项目无论批次如何进行都最终精确匹配最终验证构建。
2. **对账删除——必须执行，非可选。** `DesignSync(list_files)` 项目并 `delete_files` 删除 `components/`、`_preview/`、`tokens/`、`fonts/`、`_vendor/`、`guidelines/` 下最终 `ds-bundle/` 不包含的每个远程路径（计划的删除 glob 覆盖它们——无需新提示）。此遍存在的原因：一个由早期批次上传然后在运行中后来被丢弃、重命名或重新分组的组件对未来每次重新同步 diff 不可见——基于锚点的 diff 只能看到锚点记录的内容——所以这是它唯一能被清理的时刻；跳过它，孤儿就是永久的。删除还退役孤儿的卡片：应用从当前上传的文件重建其组件索引，所以一旦哨兵重新武装（下一步）并打开项目，卡片就消失。
3. **哨兵重新武装，然后 `_ds_sync.json` 绝对最后**，在其自己的 `write_files` 调用中——与原子路径相同的规则和原因：锚点只应为完全应用的状态担保，它在删除之后执行，这样失败的删除不会留下锚点不再看到的远程文件。然后输出项目 URL——`https://claude.ai/design/p/<projectId>`——附带最终摘要。

此路径上任何地方运行中中止（用户停止运行、会话死亡）使项目保持**无锚点**状态——文档记录的安全状态：下一次同步重新验证一切并重新上传，没有东西静默腐烂。与子技能上传章节一样，任何重试无法清除的写入/删除失败意味着**停止**——不重新武装哨兵，不写 `_ds_sync.json`。

## 编写约定头部

你刚刚花了真正的努力让这个设计系统的预览渲染——搞清楚组件必须如何包裹、需要什么 provider 和 theme 设置、什么加载顺序重要，以及哪些错误会静默产生无样式输出。这些知识在同步结束时就会蒸发，除非你在这里为一个非常特定的读者写下来。

**谁读它。** 你编写的文件被前置到生成的 README（通过 `readmeHeader` 配置键），并内联到一个*设计智能体*的系统提示中——一个使用此组件库构建应用的模型，为从不见到此文件的用户构建数百次。它不会制作 storybook 预览、运行此仓库的构建或阅读其源代码；它获得 README 和绑定产物，仅此而已。处于该位置的智能体遵循具体的、列举的指引，无法遵循不存在的指引：命名令牌，它就使用令牌；不命名类词汇，它不会猜测你的——它会发明自己的。说包裹 provider，它就包裹；不说，它大部分时候不会。所以每句话必须通过一个测试：*设计智能体能在不猜测的情况下据此行动吗？*（"遵循设计系统的约定"未通过该测试；删除它并写出约定。）

**写什么**——四个关注点，以服务于此设计系统的任何结构：

- **包裹和设置。** 如果组件需要 provider/根包裹器才能有样式（通常令牌和主题就在这里），命名它，说明没有它会破坏什么，并在最小代码片段中展示包裹——加上主题设置、加载顺序，以及任何让你花了一个预览调试周期的坑。按读者的工作过滤：它构建应用，不构建预览——工具特定的设置（storybook 怪癖、脚手架）放到 NOTES.md；用组件构建需要关心的内容放这里。
- **样式惯用法，带真实词汇。** 教这个系统的惯用法，绝不教通用的：工具类系统得到一个紧凑的家族表，使用样式源中的真实名称（Tailwind 预设精确枚举它们）；prop/theme 系统得到"无 CSS 类——通过 props 样式化"加上承载设计语言的 props；令牌系统得到 `var(--*)` 模式和真实名称。绝不导入设计系统没有的惯用法。
- **真相在哪里。** 命名智能体在样式化前应阅读的样式表/源文件（它将拥有的绑定副本，例如 `_ds/<folder>/styles.css` 及其导入）和每组件文档。阅读真实文件的智能体胜过任何摘要——你的工作是确保它知道去哪里看。
- **一个惯用法构建片段。** 一个简短的真实示例——一个库组件用于控件，设计系统的样式惯用法用于智能体自己的布局胶水。改编你的一个已验证预览：那是你知道能渲染的代码。

跨不同类型系统看起来像（说明性的，非穷尽的）：Tailwind 预设设计系统 → 家族表（`bg-surface-1`、`gap-md`、`text-body`…）+ 根包裹器；grommet 风格设计系统 → 无类，`pad`/`background`/`tone` props + ThemeProvider；chakra 风格设计系统 → 主题令牌字符串（`color="red.500"`）；CSS-modules/BEM 设计系统 → 导出的类映射以及新名称是否曾有正当理由；web-components 设计系统 → slots、属性和注册顺序。

**交付前验证。** 命名不存在之物的约定文件比没有更糟——智能体会信任它，写出无法解析的词汇，并静默交付无样式输出。提交前：你枚举的每个类、令牌、prop 和组件必须存在于构建产物中——在输出目录中对编译的样式表 grep 类/令牌；在输出目录的 `components/<group>/<Name>/` 目录中检查命名组件（你刚运行的构建为每个组件发射一个——该树是同步时的名称索引；`.ds-build-meta.json` 只携带计数），然后在 bundle 文本中（权威来源——例如像根包裹器这样的 provider 在 bundle 中发货而没有组件文件夹），再下结论。两者中都不验证 → 修复名称或删除；在源代码中有文档但构建中缺失 → 那是 NOTES.md 的发现，不是头部内容。

**预算。** 简洁——2-4k 字符覆盖所有四个关注点，真实名称胜过模糊。如果构建的大小警告触发，阅读它命名哪一侧。头部侧（头部单独超过约 31.9k）：缩短头部——它仅当自身适应 ~32k 窗口时才能在内联截断中存活；超过后，它自己的尾部被截断，正文贡献为零。正文侧：你的约定是安全的（前置，窗口内）；丢失的是生成正文的末尾——通常是组件索引的尾部。有意接受该损失，或减少同步范围（package 形态：`componentSrcMap` 排除、更窄的 `tokensGlob`；storybook 形态：同步更少的 stories）——没有正文部分修剪旋钮。

**它在哪里，以及重新运行。** 写 `.design-sync/conventions.md`，设置 `"readmeHeader": ".design-sync/conventions.md"`，提交两者——它故意是人工可编辑的。然后重新构建使 README 实际携带头部——它在构建时缝合。**重新构建规则：** 编写后的重新构建在每条路径上都是全新的驱动器运行——首次同步省略 `--remote`——因为收据和上传计划都必须描述带头部的构建；裸转换器运行会擦除 `.sync-diff.json` 和收据产物，使已上传构建无收据。（编写后重新构建的其他所有提及都遵从此规则。）每当文件已存在——无论本次运行如何分类（重新同步、配置丢失后的重新采用、从部分配置恢复）：绝不重写它——针对新构建重新运行验证 pass 并报告任何不再验证的名称（NOTES.md + 用户），提出编辑建议。编写仅在不存在 `.design-sync/conventions.md` 时发生。内容属于其作者；你的常设职责是保持其真实。
