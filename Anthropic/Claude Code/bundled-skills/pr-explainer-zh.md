未给定 PR 号——解释当前分支的待处理 PR：
1. `git log --oneline @{upstream}..HEAD` 获取提交列表（如无 upstream 则回退到 `origin/main..HEAD`）
2. `git diff @{upstream}...HEAD` 获取统一 diff

## 目标

生成一个**可分享的 PR 演练 artifact**——一个审查者在打开 diff 之前可以阅读以理解此更改做什么、为什么进行、以及应关注哪里的自包含 HTML 页面。将写作定位在首次看到此 PR 的审查者。

无论答案最终落在下方哪些部分，页面必须回答以下所有五个问题：

1. 此 PR 试图解决什么问题？
2. 为什么它是问题？
3. 我们如何解决它？
4. 我们考虑了哪些替代方案？
5. 为什么当前方法比替代方案更好？

如果 diff、PR body 和提交消息对其中之一没有证据——最常见的是 4 和 5—— plainly 说明（如"PR 没有记录考虑过哪些替代方案"）而非编造答案。

## 从解释器模板构建

加载 `artifact-explainer` 技能并从其模板构建页面，按该技能指示用 Artifact 工具发布。使用模板的**sections flavor**——保留 sections 结构，删除编号步骤。按以下方式填充槽位：

- **Lede**——此 PR 改了什么以及为什么需要它，用两三句话。如果 PR body 已经说得好，重用它。
- **Sections**——当更改有结构性故事时，以一个架构或流程图开头；否则直接跳到代码。以一个 before/after 部分开头展示用户可观察的更改（行为、API 形状或输出）；如果更改没有可观察表面则跳过。然后将 diff 分组为按材料关节切割的部分——将相关更改分组而非按文件拆分。在每个部分中，代码片段通常是主题内容本身：修剪的片段、通俗语言解释，以及审查者应仔细查看的任何东西；仅在结构或流程确实需要时添加图表（该技能的图表优先默认适用于概念解释器，而非 PR 演练，后者主要是符号内容）。以一个部分结束，涵盖 diff 中*不*显而易见的东西——diff 单独不显示的上下文（为什么选择此方法而非替代方案、尝试并拒绝了什么、有意留出的后续）。
- **Recap**——将要点重述为审查者应关注的地方。

在页面正文末尾逐字写以下行：

> Paste this URL back into Claude Code to keep iterating on these findings.

## 保持诚实

描述 diff *实际做什么*——追踪它，不要从名称推断。如果 PR 中的某些东西对你不清楚，在第 4 部分说明而非猜测。
